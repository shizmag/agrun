## Deterministic fixture rules

Use a mutex-protected event journal with `(step_id, attempt, event)` and counters,
plus Queue/SizedQueue gates per executor entry/release. Parent waits for explicit
entry events before releasing work, cancelling, or inspecting observations.
Every queue read, thread join, socket accept/read, and process reap has a generous
monotonic watchdog; watchdog expiration is a setup/test failure, never the expected
runtime timeout. No arbitrary sleeps and no absence assertions based on elapsed
wall time. End-of-run call journals prove non-execution; at intermediate barriers
assert only prerequisites/counters already observable without scheduling guesses.

Start Runtime in a controlled thread; propagate its exceptions to the test. Gates
must release in `ensure`, with bounded joins and explicit fixture process cleanup
before removing temp directories. Never leave a gate blocked waiting for work
that the expected failure/cancellation deliberately prevents.

For subprocesses use `RbConfig.ruby`, unique temporary UNIX socket paths (short
enough for platform limits), and a local fixture leader/descendant readiness
protocol. The descendant installs its TERM handler before acknowledging READY;
both then block on socket IO, not sleeps. Keep a fixture-owned liveness connection
open in each process; EOF on both after cancellation/deadline is observable exit
evidence. Do not rely solely on `kill(0, pid)` (zombies/PID reuse) or delayed
sentinel writes. Parent also records fixture PIDs/group for narrowly scoped
cleanup; no broad process kills. Ordinary same-group descendants only: detached
process/session escape is outside the documented guarantee.

## Scenario inventory

### B-01 — chain dataflow and dependency failure (C; UNTESTED)

- Setup: `a -> b -> c`; b binds a's declared text output, c binds b's. Journal
  entry/exit and exact decoded input values; gate each predecessor before return.
- +: all succeed with independently specified transformed values. Expect strict
  predecessor-success-before-entry, one attempt each, successful emitted value
  decoded through Store, and successful persisted final report.
- −: a fails; separately b fails after a succeeds. Expect each downstream step
  cancelled with no executor entry/no attempts, no final output from c, and an
  unsuccessful run. Do not infer exact mixed-status run precedence here.

### B-02 — independent branches survive unrelated failure (C; UNTESTED)

- Setup: a and b enter behind gates with concurrency 2; c depends only on b.
  Release failing a before releasing b; keep the cancellation token untouched.
- +: both roots succeed and c executes once with b's value.
- −: a fails, b and c still succeed; c must not be cancelled by a's unrelated
  failure. Expect a failed step and non-success run, not fail-fast global abort.
  Reverse root declaration order to avoid an IR-order-dependent oracle.

### B-03 — fan-in, especially late dependency failure (C/H; UNTESTED)

- Setup: a and b roots, c needs both, d needs c. Gate roots independently.
- +: finish a first while b remains gated; c must observe both predecessor
  completions before entry. Then release b and expect c/d success.
- −: a succeeds first; b fails last. c/d never enter, are cancelled with no
  attempts, and emit nothing. Repeat with a failing late and reversed declaration
  order. This targets a premature fan-in launch; not proof that one exists.

### B-04 — simultaneous root failures and fan-in accounting (C/R; UNTESTED)

- Setup: two entered roots wait at a two-party release barrier; both return
  failure, with c depending on both; an independent successful branch is gated
  separately. Release both together without assuming completion ordering.
- +: the same barrier with successful roots leads to c success exactly once.
- −: both failures must be retained exactly once with their own errors/attempts;
  c never runs, unrelated work completes, and run is non-success. Repeat one root
  timeout plus one failure: exact run-level precedence is R (U-02), not an oracle
  copied from scheduler iteration order.

### B-05 — pre-cancel and cancellation during active work (C/R; UNTESTED)

- Setup: real Cancellation token; cooperative adapter acknowledges entry, waits
  on a gate, then checks token and returns cancelled. Pending dependent and extra
  independent root permit checking no new work after cancellation.
- +: uncancelled control completes all nodes.
- − pre: cancel before run; no executor calls, all planned steps cancelled with
  zero attempts, no outputs, cancelled run/report.
- − during: concurrency 1; after first entry, cancel token before releasing its
  gate. Active attempt observes the same cancelled token and returns cancelled;
  queued nodes never enter; final report persists. Also cancel after a successful
  predecessor but before its gated active sibling finishes; retain already
  successful work. Exact precedence with independent failure is R (U-02).
- Explicitly do not demand forced thread termination for an uncooperative custom
  executor; only subprocess adapters promise group termination (U-03).

### B-06 — timeout and descendant process-group termination (C/R; UNTESTED)

- Setup: call public ProcessRunner with local leader and child readiness/liveness
  sockets; each parameterized for default TERM handling or ignoring TERM. Give
  ample startup budget; if READY is not received before the runtime deadline,
  classify setup failure rather than crediting descendant coverage.
- +: command released before deadline exits successfully, streams/exit status
  are captured, liveness sockets close, no fixture process remains owned.
- − timeout: both are READY and remain blocked until deadline; expect timeout,
  bounded return and both liveness EOFs. TERM-ignoring child tests escalation;
  also leader exits while child holds stdout/stderr open to exercise that boundary.
- − cancel: cancel only after both READY; expect cancelled rather than timeout,
  no surviving same-group fixture descendants, bounded return.
- − pre-cancel: valid local command would connect/write a marker if spawned;
  pre-cancel means cancelled with no connection/marker, using completed call as
  boundary (not timed absence). Test no-op success as control.
- Runtime integration: use Shell wrapping this fixture, check step terminal
  status and cancelled dependent. Separately, a local custom executor signals
  entry then blocks interruptibly on a Queue with cleanup in ensure: exercise
  the observable Ruby timeout fallback, expecting a timeout attempt and no
  dependent execution, with an external watchdog larger than the configured
  deadline. This is not a promise of safe arbitrary executor preemption.
  Current source wraps execute in `Timeout.timeout(step["timeout"] + 0.1)`;
  do not assert that implementation grace as a public latency contract. Test
  cleanup is fixture-owned; safe subprocess cleanup guarantees remain specific
  to ProcessRunner.

### B-07 — transport retry then recovery (C/R; UNTESTED)

- Setup: scripted adapter returns failure with error type `transport` for attempt
  1, then valid success; journal request attempt and workspace. Gate retry entry
  and use no external side effects. Retries=1; downstream binds recovered output.
- +: two calls, attempt numbers 1/2, distinct fresh workspaces, both attempts in
  report, final success and downstream exactly once with recovered value.
- −: retries=0 gives one failure call and cancelled downstream, no success output.
  Also cancel at a barrier before releasing first transport failure: no second
  executor call after cancellation. Exact final status is R (U-02).
- This verifies the documented transport label policy only, not replay safety;
  side-effect safety remains U-01 and must not be silently assumed.

### B-08 — exhausted retries and nonretry failures (C/R; UNTESTED)

- Setup: bounded scripted sequence, retries parameter 0/1/2, independent success
  branch, and dependent of failing step.
- +: a final permitted success makes total calls `retries + 1` and unblocks
  dependent. Control a first-attempt success: no unnecessary retry.
- − exhaustion: transport failure every time: exactly `retries + 1` calls and
  attempt records, final failure, dependent cancelled, independent success kept.
- − nonretry: logical failure, blocked, unknown, timeout, cancelled, executor
  exception, and artifact-validation error each with retries=2. Expect no retry
  absent a transport classification, no dependent launch, no successful emitted
  artifact. Exact normalization of exception/invalid-result status is U-04.
  Shape of transport error (`type` string key vs symbol/malformed error) requires
  reviewer-approved input contract; do not broaden it from implementation quirks.

### B-09 — invalid executor results fail closed (C/R/H; UNTESTED)

- Setup: one producer, one dependent, one independent success branch; return a
  separate invalid specimen per test. Retried count configured positive.
- +: declared text output with valid Result success is stored, decoded and
  consumed; declared-output filtering permits unrelated extra outputs per
  `CONTRACTS.md:19` (do not incorrectly require their rejection).
- −: missing required output; wrong concrete artifact type; nil/non-Result;
  invalid/unrecognized status; non-Hash outputs; invalid JSON value. Never report
  successful producer/dependent or publish a valid final emit from invalid data;
  independent branch still completes. Missing/type errors are documented runtime
  checks; arbitrary Result shape normalization is R (U-04).
- Need reviewer decision on retaining partial output artifacts when a later
  output fails validation (U-05); require no successful final output, not atomic
  Store rollback that no source contract promises.

### B-10 — per-step and per-attempt workspace isolation (C; UNTESTED)

- Setup: immutable repository input with known bytes; two concurrent roots get
  the same artifact. On entry each writes a distinct local marker then waits on
  barriers; each reads its own and the other's marker before returning a declared
  repository output. Use runtime-returned paths, not assumed internal layout.
- +: distinct step workspaces/input copies, own edits visible, sibling edits
  absent, original repository unchanged, each stored output has expected bytes.
- − retry: attempt 1 writes a poison marker then returns transport failure;
  attempt 2 sees pristine input/no poison, succeeds; attempt directories differ.
  After both complete reread original and stored input snapshot bytes.
- This asserts directory/data separation, not hostile-code containment or a
  security sandbox; symlink attacks and arbitrary host access are outside scope.

### B-11 — concurrency bound and readiness (C; UNTESTED)

- Setup: more independent nodes than slots, active/high-water counters under one
  mutex; each call increments on entry and decrements in ensure before return.
  Entered/release queues prove overlap without duration comparisons.
- +: concurrency=2 reaches exactly two simultaneous entered calls before any
  release; then release controlled batches, all execute once, high-water <=2.
  Repeat concurrency=1 (no overlap) and 32 with enough gated nodes to exercise
  the documented upper boundary, using generous watchdogs.
- −: inject one failure/transport retry while slots are occupied; high-water
  remains bounded, permitted retry proceeds when a slot is free, no deadlock or
  lost completion. Reject 0, 33, negative, string, nil, and noninteger concurrency
  before any executor entry; exact error wording is not a contract.

## Uncertainties to resolve before executable assertions freeze

| ID | Decision needed / proposed safe boundary |
| --- | --- |
| U-01 | **Safe retry ambiguity.** Docs say transport-only retries, but transport failure can occur after effects committed. No idempotency key, pre-effect proof, retry-safe flag, reconciliation, or caller declaration is specified. Test only local side-effect-free scripted retries now; do not claim safe replay/exactly-once. Parent/reviewer must decide whether this is an M0.1 contract clarification or deferred limitation. |
| U-02 | Mixed failure/timeout/cancel/blocked/unknown aggregate precedence and error selection are unspecified. Assert each step outcome plus run non-success until a normative table is approved; never hard-code current declaration-order behavior. Race at completion versus cancellation has no total-order promise. |
| U-03 | Current Runtime has Ruby `Timeout.timeout(step["timeout"] + 0.1)` fallback; test its observable timeout with an interruptible local Queue fixture. Arbitrary trusted Ruby cancellation remains cooperative, distinct from bounded ProcessRunner process-group termination. A fallback exception is not safe arbitrary executor preemption, thread-safe cleanup, a security guarantee, or external effect rollback. Confirm the normative latency/cleanup boundary rather than assuming there is no fallback. |
| U-04 | Result status vocabulary is documented, but behavior for nil/non-Result, invalid statuses, malformed error/outputs and unexpected executor exceptions is not fully specified. Proposed fail-closed containment should be reviewer-approved; an exception escaping the public run boundary is a finding to classify, not automatically accepted behavior. |
| U-05 | Artifact validation can fail after earlier outputs were stored. Atomic output publication/rollback and partial emit behavior on failed runs are unspecified; keep artifact-store transaction claims out of B without coordinated contract work. |
| U-06 | Exact per-run timeout bounds depend on startup/OS load; watchdogs are bounded failure protection, not latency SLAs. POSIX-only process fixtures may require an explicit platform guard, but must not silently skip on the current macOS target. |

## Reporting and exclusions

After freeze, each B family records pass/fail/blocked, command, assertion evidence,
and failure classification: contract violation, contract ambiguity, fixture/setup
failure, or out-of-scope limitation. A green control is mandatory before crediting
an adversarial fixture. No existing behavior is automatically the oracle. Keep
execution status distinct from benchmark/evaluation verdict; B does not add a new
verdict field to Runtime.

No crash recovery, resume/replay after process death, durable scheduler, provider
availability, hidden evaluation procedures, security sandbox, detached process
containment, or live adapter certification is promised or tested by this plan.

### Focused EPERM diagnostic (2026-11-14; no production changes)

Classification: **production cleanup race exposed by Darwin zombie-group signal
semantics**, not a blanket prohibition on signaling subprocess groups. Platform:
Darwin 25.0.0 arm64 (xnu-12377.1.9~141), Ruby 4.0.9, UID 501.

Disposable-directory diagnostic subclassed ProcessRunner only in an inline Ruby
script to log `signal_group`, with two UNIX-socket readiness acknowledgements.
Leader 88387 and descendant 88388 both reported PGID 88387 / UID 501; caller
88385 had its own PGID 88385. TERM succeeded; first KILL succeeded. A subsequent
KILL to -88387 raised `Errno::EPERM: Operation not permitted` after leader lookup
already returned ESRCH. Another run captured leader 96203 / descendant 96204,
both PGID 96203 / UID 501: TERM and first KILL succeeded; the next signal snapshot
showed the leader in state Z. No PID-reuse evidence was observed.

A minimal independent control spawned only `/bin/sleep 30` in a fresh process
group and synchronized on `ps` reporting state Z after the first successful
group KILL (bounded 3-second watchdog, no arbitrary sleep). Three repetitions:

| PID / PGID | live group KILL | zombie group KILL | after `Process.wait(pid)` |
| --- | --- | --- | --- |
| 96797 | 1 (success) | EPERM | ESRCH |
| 96799 | 1 (success) | EPERM | ESRCH |
| 96801 | 1 (success) | EPERM | ESRCH |

Thus EPERM here does not establish a live inaccessible descendant. It is
reproducible for an unreaped dead same-user group leader, without this test's
descendant fixture. It is not evidence that every EPERM is harmless.

Source explanation: `lib/agent_runtime/adapters/process_runner.rb:37-41` repeats
KILL each loop after escalation; `lib/agent_runtime/adapters/process_runner.rb:53-58`
uses nonblocking wait, which may not yet reap a just-killed process. An ensuing
KILL can therefore hit the zombie window. The body rescue at
`lib/agent_runtime/adapters/process_runner.rb:61-62` catches SystemCallError,
but the unconditional ensure signal at
`lib/agent_runtime/adapters/process_runner.rb:65` raises EPERM again and masks
the result; it also bypasses the later blocking reap at
`lib/agent_runtime/adapters/process_runner.rb:66-71`. `signal_group` at
`lib/agent_runtime/adapters/process_runner.rb:78-81` rescues ESRCH only.
This establishes a failure mechanism, not a proposed blanket EPERM rescue.
