# M1.1c frozen scoring contract: scoped `nl2repo-audited-v2`

Contract version: **`nl2repo-audited-v2`**. Scope: deterministic evaluation of **benign,
non-interfering submissions** with a pinned pytest procedure. This document
defines acceptance semantics, not evidence that an implementation has passed
them. Freeze candidate for parent approval; no production API change is authorized
by this document. Read with `docs/m1.1c-trust-boundaries.md`.

Freeze record (2026-11-14): parent decisions fix the protocol, `quality_basis`
values, `passed`/`total` aliases and scoped trust labels recorded below. Reviewer
comments and final semantic approval remain pending; this is not a record that
review has completed. No production work is authorized before that review gate.

`nl2repo-audited-v2` is not the official pinned legacy parser, not a paper-compatible
score, and not an adversarially authenticated grader. For this protocol only, the
explicit benign trust model replaces the old universal authentication gate; it
permits scoped quality results without claiming candidate-resistant collection.
Historical protocols and evidence retain their original stronger claim boundaries
and blocked/untrusted outcomes. The public-contract amendment must make this
version-specific exception explicit before implementation. A diagnostic observation
must not become a scoped quality result simply because it has structured JSON.

## 1. Frozen unit, numerator and denominator

The scoring unit is one **canonical pytest case identity**, not an output line,
command, file, collected summary count or repository-level pass/fail decision.

Before candidate grading, an operator-controlled preflight freezes a task case
manifest in the pinned environment using the exact test assets and procedure.
The manifest contains a nonempty, sorted, unique list of expected case identities
and its digest. Candidate collection must never redefine this list. The upstream
declared count is retained separately, even when it differs from this inventory.
Collection under a known-good reference is a preflight/control technique, not a
license to copy the reference into solver workspaces or candidate grading trees.

For one task and attempt:

* `denominator = expected_case_ids.length`, fixed before seeing candidate results.
* `numerator = count(expected cases with accepted outcome passed)`.
* `score = numerator / denominator`, a finite number in `[0, 1]`.
* `verdict = pass` exactly when numerator equals denominator; otherwise `fail`.
* Preserve integer numerator and denominator alongside the normalized score.

Frozen report literals are `protocol: nl2repo-audited-v2` and
`quality_basis: validated_quality_result` for accepted complete case results, or
`quality_basis: candidate_collection_failure` for the supported collection-failure
rule. Quality-bearing results use `trust: audited` only together with
`trust_scope: benign_ordinary_submissions`; there is no `authenticated` flag.
The existing runner's
`passed`/`total` fields carry numerator/denominator; a parser may expose richer
outcome counts without becoming the score authority. Keep the benign trust-model
qualifier in bound evidence and public reporting alongside these labels.

Evidence also records integer `expected`, `collected`, `executed`, `failed` and
`skipped` counts. `expected` equals the denominator; `collected` counts unique
expected node IDs actually collected, and `executed` counts unique cases whose
call phase ran (including failed and xfail/xpass calls, excluding setup skips and
setup errors). `failed` counts terminal ordinary failed/error cases once, including
setup/teardown errors; `skipped` counts terminal ordinary skips, not XFAIL. Preserve
separate xfail/xpass/error/not-run counts and raw phase evidence so these diagnostic
counts are not mistaken for a partition or used to reconstruct the denominator.

No clamp repairs inconsistent evidence. A numerator exceeding the denominator,
an empty denominator, an unexpected case or an ambiguous duplicate is a protocol
error with no score. A declared-count discrepancy is a recorded preflight finding;
it requires an explicit task-specific approval bound into the procedure, not an
automatic substitution or a silent claim of legacy compatibility.

### Canonical identities and command overlap

An identity is the exact pytest node ID relative to a frozen test root, including
class, function and complete parameterization suffix. Bind it to task ID and
test-assets digest. Normalize only the known absolute test-root prefix and path
separator to `/`; do not lowercase, strip parameters, collapse internal whitespace
or use display-name/summary-text matching. Reject paths outside that root.

Freeze command order and an explicit case-to-command ownership map. The same
canonical case selected by overlapping commands contributes **once**. Any
intentional independent repetition belongs in a distinct experiment repetition,
not an extra passing case. Do not resolve conflicting or repeated terminal
records by choosing the best result or silently taking the last one. Phase
records for setup/call/teardown are combined into one terminal case outcome;
legitimate phase records are not duplicate cases. Rerun plugins and alternate
collection roots require a separately versioned policy, not ad hoc deduplication.

## 2. Case outcomes

| Observation | Numerator | Denominator | Required interpretation |
| --- | --- | --- | --- |
| Setup, call and teardown complete successfully | +1 | Unchanged | `passed` |
| Assertion failure, or candidate-attributable setup/teardown error | +0 | Unchanged | `failed` or `error`, retain phase and reason |
| Skip, including setup-time skip | +0 | Unchanged | `skipped`; never a pass or denominator reduction |
| Expected failure (`xfail`) | +0 | Unchanged | `xfailed`; exposes unmet behavior rather than rewarding a mark |
| Unexpected pass (`xpass`), strict or non-strict | +0 | Unchanged | `xpassed`; never silently promoted to ordinary pass |
| Case not run because of a proven candidate collection/import failure | +0 | Unchanged | Explicitly `not_run_candidate_error` with causal collection evidence |
| Missing terminal event without such a proven cause | No score | Retained for reporting | Incomplete evidence/infrastructure outcome, not a zero-quality result |

An XPASS therefore prevents the full-pass verdict even when pytest itself exits
zero. Outcome categories, including non-strict XPASS, must come from structured
pytest lifecycle information, not terminal text. A passing call followed by a
teardown failure is not a passed case. Warnings do not change the numerator unless
the frozen procedure explicitly promotes them to errors.

## 3. Execution status is not quality

Retain the existing execution-status/evaluation-verdict separation. Successful
grading means the scoped procedure completed and produced accepted evidence;
it does **not** mean the candidate passed. Non-success grading has nullable
score/verdict, never an invented quality zero. Exact existing transport status
names remain unchanged; the following are evidence reason categories, not a new
public status enum.

| Category | Examples | Quality treatment |
| --- | --- | --- |
| Candidate semantic failure | Assertion failure; missing candidate module/API; candidate syntax/import error against a healthy frozen harness | Completed, causally supported scoped evaluation may score zero or partial credit |
| Preflight/environment unavailable | Missing pytest/plugin/dependency/test asset/image; unsupported architecture; reference control cannot collect; invalid case manifest | Blocked/unavailable; null score and verdict |
| Transport/infrastructure failure | Docker/runtime failure; mount error; collector startup failure; disk/resource failure unrelated to candidate behavior | Failure/blocked as appropriate; null score and verdict |
| Timeout/cancellation | Deadline reached or operator cancellation, even after some passes | Timeout/cancelled takes precedence; null score and verdict; retain partial diagnostics |
| Evidence/protocol failure | Missing/truncated/malformed results; wrong identities/digests; duplicates; unexpected cases; absent completion; unexplained missing cases; interference | Failure/blocked/untrusted as appropriate; null score and verdict |

### Collection and import errors

Do not equate all pytest exit 2 outcomes with infrastructure failure, and do not
equate every `ImportError` with candidate failure. Attribution needs the preflight
inventory, healthy harness evidence, failing import path/phase and import
provenance. Missing candidate code or dependencies that the frozen task explicitly
requires the submission to provide can be candidate errors. Missing harness
dependencies, tests, plugins or runtime support are infrastructure problems.
Ambiguous attribution fails closed with no score.

Attribution rules must be explicit task-specific audited capabilities, not a
generic exception-name heuristic. An initial selected-task implementation may
support only evaluator-proven absence of a frozen required module before any
candidate import. It must then reject other import errors and mixed partial
collection results as unsupported/unscored until a reviewed rule exists. A module
that exists but raises on import is not proven absent. Do not use candidate
`find_spec`, import hooks or stdout as a privileged absence proof.

A candidate collection failure can establish a semantic failure only when the
collector completes normally, records the causal failure and explicitly accounts
for the expected cases that could not run. Those cases remain in the denominator
with `not_run_candidate_error`; already completed cases can retain credit. A
collector that merely disappears, a subprocess killed mid-import, or an empty
result file cannot use this exception. Empty collection on an empty candidate is
not a successful zero-case task.

The procedure must define and verify the relationship between pytest exit code,
collection errors and terminal outcomes. Exit 1 can be a valid failed evaluation;
exit 0 alone cannot establish success. Usage/internal errors, no-tests exit and
unexplained nonzero exits are not normalized to semantic zero. Do not accept a
partial result just because it contains some passing records.

## 4. Required evidence and versioning

Every accepted attempt must bind the **actual submitted bytes**, not merely a
source path or pre-solver input, to:

1. Store submission artifact/tree digest and the immutable attempt/cell identity.
2. Task ID, dataset repository/revision, public specification digest, upstream
   declared count, expected-case manifest and its digest.
3. Exact test-assets digest; grader/collector source digest and result schema
   version; scoring protocol `nl2repo-audited-v2` and explicit benign trust-model label.
4. Procedure digest covering commands/argv, order, ownership map, working directory,
   test root, environment variables, cleanup/materialization/import policy,
   pytest/plugin versions and outcome policy. No implicit host configuration.
5. Immutable image digest, platform, effective runtime/resource/network policy,
   and relevant environment fingerprint; mutable image tags alone are inadequate.
6. Preflight/control evidence identity and approval findings, including any
   declared-versus-collected discrepancy and validity scope.
7. Raw phase/collection outcomes, command exit codes, completeness markers and
   execution status/reasons; normalized case accounting, numerator, denominator,
   score and verdict, plus the frozen evidence counts above. Preserve logs as
   diagnostics, not scoring authority.

Validate bindings before normalization and when independently regrading. A
regrade creates a new attempt/evidence record for the same verified artifact;
it never mutates the original observation. Changed tests, denominator, outcome
rules, identity normalization, environment or procedure mean a distinct evidence
identity. Semantic scoring changes require a new protocol version, not reuse of
`nl2repo-audited-v2`. Hidden assets remain grader-private even when their digests are
retained in reports. Evidence digests detect mismatches; they do not authenticate
a collector that candidate code can impersonate.

## 5. Preflight and promotion gates

Preflight is task/procedure/environment specific. Require authorized, locally
available assets; digest verification; healthy pytest/collector startup; expected
case manifest; known-good reference control; incomplete/empty negative control;
and checks for clean materialization and import origin. A reference pass alone is
insufficient. Reference controls are grader-only. Keep controls separate from
solver capability cells and persist their real outcomes rather than manufacturing
passed score files. Bind the preflight report to all inputs above; stale controls
cannot validate a different image, test suite or collector.

Passing preflight establishes a bounded functioning harness, not hidden-test
confidentiality, adversarial integrity, universal environment compatibility or
benchmark-wide readiness. A selected-task implementation must reject unsupported
tasks explicitly rather than extrapolating one task's approval to 104 tasks.
Preflight must not download assets, invoke providers or run Docker as a side
effect of ordinary offline tests. Operational execution needs its own opt-in.

## 6. Missing results, coverage and historical comparability

Persist all planned task/solver/model/repetition cells, including skipped,
not-started, blocked, unavailable and failed grading cells. Missing results are
not passes, semantic zeroes or permission to remove cells from coverage. Report
quality only for accepted completed evaluations, with the evaluated/planned count
and every excluded outcome/reason beside it. A complete-case mean is explicitly a
conditional statistic, never a full benchmark score.

For accepted tasks, report both the macro mean of per-task rates and, if useful,
the micro ratio of summed numerators to summed denominators, labeled distinctly.
Do not pool repetitions or choose the best repetition without an explicit frozen
aggregation rule. Preserve the existing report convention: average accepted
repetitions within each task before averaging tasks, with repetition coverage
explicit. Never infer either aggregate from legacy raw `score` fields.

Legacy native behavior uses textual passed-count matches and a declared total,
caps its normalized rate at one, and does not account for identities, skips,
xfails or xpasses. Its raw passed count is not an `nl2repo-audited-v2` numerator. Preserve
legacy evidence with its original label; do not relabel M1.1b's observed
23/23 reference or 1/23 incomplete result as audited acceptance. Any comparison
must use the same submitted artifact and task assets, disclose differences in
materialization/commands/environment/denominator, and report protocols side by
side. Agreement on a control is not equivalence to official or published scores.
