# M1.2b: installed OpenCode request-boundary evidence

## Scope and reproducibility

This is capability evidence, **not** authorization to use the real-provider
adapter, a claim of complete mediation, or a network sandbox. The M1.2a fixture
guard is unchanged by this slice. No external model/provider was called for these probes.

Observed on 2026-11-15 using the installed macOS arm64 executable:

- `/Users/vladimirkasterin/.opencode/bin/opencode`
- `opencode v2.3.0`
- SHA-256 `9f3147cae4ca323827d3ca39451b0d3431b2906e79a08e9b09d1eb34bb703f52`

Run the separately opted-in integration probes:

```sh
mise exec -- env AGRU_OPENCODE_BOUNDARY=1 \
  AGRU_OPENCODE_BOUNDARY_BINARY=/absolute/path/to/opencode \
  bundle exec ruby -Itest test/m12b_provider_boundary_test.rb
```

Default test runs skip these installed-binary probes. They launch a private
`--standalone` server in a new workspace, clear inherited environment variables,
use isolated HOME/XDG/config/cache/data/state paths, disable models fetching and
auto-update, and configure both main and small models to a loopback-only custom
provider. The mock listens on `127.0.0.1` with an ephemeral port. API keys
are test-only dummy strings. There are no symlinks to user configuration,
credentials or memory. This is configuration isolation, not an OS egress filter;
it cannot prove that a future executable makes no other network connections.

The intended transport is `@opencode/ai/providers/openai-compatible`, with
`settings.transport = "http"`. The real binary sends
`POST /v1/chat/completions` to the mock. Its response is a deterministic SSE chat
completion, not an adapter fixture process pretending to be OpenCode.

## Actual launch-class integration

`AgentRuntime::Execution::OpenCodeLaunch` binds an executable SHA-256, freezes the
primary and small-model selector to `omniroute/cx/gpt-6-luna-low`, upstream model
and route to `cx/gpt-6-luna-low`, endpoint to `http://localhost:20128/v1`, and
native HTTP transport. There are no live configuration numerical token/context
caps. The earlier boundary mock's context/output values are fixture metadata,
not live caps. It generates secret-free config outside the workspace, disables
project config, sets no plugins or MCP servers, and yields a scrubbed environment
containing only the explicitly supplied credential. Callers must clear inherited
environment (`unsetenv_others: true` or equivalent explicit removal).

Tests exercise this **actual generated configuration**, replacing only its
`baseURL` in a test-owned temporary file with the ephemeral mock URL. They never
bind or contact port 20128. Real OpenCode sends exact wire model
`cx/gpt-6-luna-low` and the dummy environment credential. Mock-forced tool calls
show shell, subagent, webfetch, websearch, and execute are unavailable; outside
`/etc/hosts` read and worktree removal are denied. Shell marker never exists.
Workspace read and patch succeed, while an outside-workspace patch is denied.
An explicit unauthorized `openai/gpt-4.1` selection returns `provider.no-route`
with zero mock requests rather than silently falling back to the configured model.

The installed binary's `FileAccess.resolve` normalizes workspace file permission
resources to relative paths; worktree removal checks `edit` against an absolute
directory. Permissions permit read/edit while a hard `tool.use` policy denies
`edit:/*`. Outside file reads/patches separately fail `external_directory`.
These are version-specific application controls, not an OS filesystem sandbox.
Provider policies deny `*` then allow only `omniroute`; skills/plugins/MCP have
deny policies in addition to empty plugin/MCP configuration.

Important residual: `skill` remains advertised and reaches skill lookup,
returning `Unable to load skill nonexistent-boundary`, rather than permission
denial. An injected project `.opencode/skills/boundary-skill/SKILL.md` also
returns lookup failure without disclosing its sentinel content. Removing the
skill policy in a diagnostic control did not make that fixture load, so this is
**not** proof of skill-policy enforcement. The advertised surface was
`opencode_worktree_remove`, `patch`, `read`,
and `skill`; wildcard deny is not a tool-visibility allowlist. This configuration
is **not** proven to disable skill execution or restrict all effects to workspace
files. Do not advertise a read/edit-only sandbox. Any pilot gate must separately
establish a fresh workspace with no skills/memory and private HOME/XDG state.
No symlink-escape test exists yet; directory separation is not a sandbox.

Constructor API:
`OpenCodeLaunch.new(executable:, executable_sha256:, credential:)`.
Accessors: `executable`, `executable_sha256`, `model_profile` (selector), `scope`
(upstream model), `argv`, and secret-free `to_h`.
`with_environment(workspace:) { |env| ... }` cleans per-attempt state on block
exit and re-verifies the executable hash before yielding. It does not enforce
hard request/spend bounds. Credential content is excluded from `inspect`.

Recorded test-first result: `test/opencode_launch_test.rb` initially failed to
load the nonexistent class; implementation then passed 2 tests / 20 assertions.
Installed-binary suite passed **19 tests / 108 assertions** (2026-11-15), including
positive workspace read/edit, injected project skill and provider no-fallback
probes. Launch unit tests passed **2 tests / 24 assertions**; owned Ruby files
pass Standard Ruby.

The tests were written before probing. Initial execution failed (no hook events,
request still dispatched) because the test plugin had an unterminated JavaScript
string; OpenCode logged `failed to load plugin` and continued. Correcting the
plugin to use `Plugin.define`, escaping the JSONL newline, and using
`event.request.headers.set(...)` made the hook/veto tests pass. This failure is
important negative evidence: plugin configuration alone is not activation proof.
It is not a red/green production-adapter implementation; the separately authorized
production change in this slice is the isolated launch configuration helper.

## Not established / must not be advertised as enforcement

- **Subagents:** no successful task-tool/subagent dispatch has been exercised here;
  injected subagent calls are rejected as unavailable by the actual launch config.
  Root-session hooks cannot be assumed to cover descendants. Accounting scope
  and activation must be demonstrated for each child session.
- **Fallback:** no WebSocket-to-HTTP fallback was exercised by this HTTP-only
  provider. Do not relabel the native HTTP retry test as fallback coverage.
- **WebSocket and other unobserved transports:** unsupported by these probes.
  No claim covers subprocess SDKs, plugin-originated fetch, MCP tools, other
  native drivers, or arbitrary trusted Ruby/tool code.
- **Auxiliary:** title was observed; summary, compaction, permission, and other
  auxiliary kinds have not been exercised.
- **Cancellation:** killing a process is not a provider-side abort guarantee.
  An in-flight request has possible usage and must remain conservatively charged
  or unknown until trustworthy settlement.
- **Hook failures:** missing/malformed plugin load fails open in OpenCode. This
  requires an independent AGRU capability/activation gate before authorizing a
  live run, not optimistic handling of plugin configuration or stdout alone.
- **Accounting:** this harness establishes dispatch ordering only, not monetary
  estimates, token bounds, reservation atomicity, or durable event provenance.

## Proposed integration contract (coordinate before implementation)

Keep the fixture-only adapter path unchanged until a distinct explicitly opted-in
live profile has a designed API. A candidate profile must pin an executable and
capability fingerprint, allowlist the proven native HTTP protocol/transport,
configure all auxiliary models explicitly, and refuse unsupported or unobserved
transports. Request admission should call an AGRU-owned reservation operation
from the pre-dispatch hook and throw on denial. Every invocation, including
retries and auxiliary requests, needs its own bounded reservation and evidence;
known denial must not become a retryable transport failure.

Plugin readiness must be independently attested before model dispatch is
authorized. A readiness event alone cannot make arbitrary transports safe;
absence of mediation evidence remains unknown/unbounded rather than success.
If OpenCode cannot guarantee that preflight gate for a candidate mode, deny that
mode. A gateway is **not** implemented or proposed as a shortcut in this slice.

Public documentation consulted for syntax (not a substitute for pinned-source
review by the adapter owner):

- <https://opencode.ai/docs/providers>
- <https://opencode.ai/docs/cli>
- <https://opencode.ai/docs/build/plugins>
- <https://opencode.ai/docs/build/plugins/server>

The current server-plugin documentation explicitly distinguishes native HTTP
hooks from WebSocket hooks and says HTTP hooks never see WebSocket traffic.
Source-level completeness and stronger activation guarantees must be coordinated
with the parent/adapter owners; neither is inferred from a version string.
