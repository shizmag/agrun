# M1.1: NL2Repo-Bench protocol audit

Audit date: **2026-11-14**. This is a source/protocol audit, **not an operational
validation**. No container images were downloaded, no native grader or remote
sandbox was run, and no task score is established. Docker daemon availability is
a reported integration blocker, not something this audit independently proved.
The companion metadata is `benchmarks/nl2repo/manifest.json` (schema version 1).

## Task identity and the 104/103 discrepancy

The official pinned `test_files/` contains **104 directories**, each with
`start.md`, `test_case_count.txt`, `test_commands.json`, and `test_files.json`.
The fixed expected-test denominators sum to **25,640**. Directory basenames are
task IDs; the manifest enumerates all IDs in sorted order, exact commands and
listed test paths, plus SHA-256 identities for the four metadata/spec files.
Counts are metadata, not independently recollected tests.

The [official README, lines 3–5](https://github.com/multimodal-art-projection/NL2RepoBench/blob/781a1da1ee41fb8edb0bed22f586d69111610edf/readme.md#L3-L5)
and paper §3.2 say 104. The [adaptation README, lines 24–39](https://github.com/EnvCommons/NL2RepoBench/blob/61d26cc0abd084ece8f5d805dcbd3f806a291f15/README.md#L24-L39)
says 103, excluding **`arxiv-mcp-server`**, allegedly because its GHCR image is
missing. Its category counts nevertheless sum to 104. No generated
`data/tasks.json` is committed at the adaptation pin. Its
[`prepare_data.py:38–115`](https://github.com/EnvCommons/NL2RepoBench/blob/61d26cc0abd084ece8f5d805dcbd3f806a291f15/prepare_data.py#L38-L115)
clones the current unpinned official HEAD (or reuses a pre-existing checkout),
then extracts every valid directory; it does **not** implement that exclusion.
Therefore this audit does not invent a versioned 103-ID adaptation dataset or
independently certify the missing-image claim. Manifest membership is official
104; the one README exclusion is recorded explicitly.

## Native preparation, commands and scoring

The source authority is
[`openhands/post_processor.py`](https://github.com/multimodal-art-projection/NL2RepoBench/blob/781a1da1ee41fb8edb0bed22f586d69111610edf/openhands/post_processor.py).
Its SHA-256 is recorded in the manifest. Pipeline order:

1. Archive the submitted workspace before mutation (lines 92–116).
2. Recursively strip package configuration basenames (lines 197–228):
   `setup.py`, `pyproject.toml`, `setup.cfg`, `requirements.txt`,
   `requirements-dev.txt`, `requirements-test.txt`, `tox.ini`, `pytest.ini`,
   `poetry.lock`, `Pipfile`, `Pipfile.lock`, `environment.yml`, `conda-env.yaml`,
   `manifest.in`, `MANIFEST.in`.
3. Remove submitted paths listed in the task's `test_files.json` (lines 231–262).
4. Build an evaluation image with
   `FROM --platform=linux/amd64 ghcr.io/multimodal-art-projection/nl2repobench/<id>:1.0`,
   `COPY workspace /workspace`, `WORKDIR /workspace`, and
   `ENV PYTHONPATH=/workspace:$PYTHONPATH` (lines 282–295). This is an overlay,
   not a clean reconstruction that first deletes the base-image implementation.
5. Execute every task command, in order, with working directory `/workspace`
   (lines 341–426). Commands and outputs/exit codes are recorded; the loop
   continues after command failures. Do not replace the exact command sequence
   with a generic `pytest` invocation.
6. `analyze_pytest_results(command_results, total_test_cases, logger)`
   (lines 429–483) examines only commands containing `pytest` case-insensitively.
   For each output line it adds the **first** regex match `r'(\d+) passed'`,
   likewise failed/error counts. Its `success_rate` is
   `min(passed / total_test_cases, 1)` for a positive fixed denominator.
   Exit codes do not gate that fraction. Output is not an authenticated test
   report, and duplicate summaries may overcount.

Examples of exact metadata commands:

```text
aiofiles:
  pip install -e .
  pytest --continue-on-collection-errors tests
arxiv-mcp-server:
  touch README.md && pip install -e .
  pytest --continue-on-collection-errors tests
asteval:
  echo "version = '0.0.1'" > asteval/version.py
  pip install -e .
  pytest --continue-on-collection-errors tests
```

All 104 exact command lists are in the manifest. Preparation sometimes writes
source-adjacent files and installs editable packages; these are part of the
native procedure, not solver achievements. The manuscript §3.1.3 describes
upstream baseline verification, environment fixes without changing functional
source, and relaxed non-functional build constraints. These are author claims;
this audit did not reproduce their baselines or inspect image contents.

`only_test.py:15–38` reports `test_score`/`score` as the **raw passed count**,
not the capped fraction. Its wrapper `status` describes processing completion,
not correctness. Keep process status, native observed counts and evaluation
verdict separate. Do not present the raw count as a normalized benchmark score
or silently choose a cross-task aggregation rule from this wrapper.

## Standalone invocation and limitations

The documented full workflow is `python main.py` from the official repository,
with dependencies from its `requirements.txt`, Docker, OpenHands configuration,
and the images documented in `readme.md:15–22`:
`docker.all-hands.dev/all-hands-ai/openhands:0.56` and
`docker.all-hands.dev/all-hands-ai/runtime:0.56-nikolaik`.
This includes solver execution; it is not a standalone grader CLI.

The shipped `python only_test.py` entry point is **hardcoded** at lines 50–68 to
task `math-verify` and workspace UUID `6b4574e2-c164-4846-ae11-b54a42f577bc`.
It is not an arbitrary `--task/--submission` evaluator. A host-side standalone
adapter can load `test_data_service.read_all_test_data()`, select exactly one
`TestData.proName`, and call
`post_process_task(task_uuid, workspace_path, test_data, logger)` against a
disposable submission copy. That is an integration design, **not a command
validated here**; imports, Docker access, fixed working-directory assumptions,
mutation and cleanup must be exercised before claiming standalone operation.

## Adaptation differences and isolation

[`nl2repobench.py:110–159`](https://github.com/EnvCommons/NL2RepoBench/blob/61d26cc0abd084ece8f5d805dcbd3f806a291f15/nl2repobench.py#L110-L159)
requires an OpenReward API key, requests a `1:2` sandbox with network enabled,
copies `/workspace` to **`/workspace_orig`**, then empties `/workspace`.
The unrestricted bash tool shares this sandbox. The reference source and tests
therefore remain reachable by the solver; directory separation is not a
security boundary. Network access adds possible public-source retrieval.

[`nl2repobench.py:226–310`](https://github.com/EnvCommons/NL2RepoBench/blob/61d26cc0abd084ece8f5d805dcbd3f806a291f15/nl2repobench.py#L226-L310)
copies `/workspace_orig` to `/workspace_eval`, strips agent configs/listed test
paths, and overlays the agent copy. Missing submitted implementation files can
be inherited from the reference copy. The official Docker `COPY` overlay has
the analogous **conditional** risk if the base image retains source; the actual
images were not inspected. Neither pipeline proves evaluation uses only the
actual submitted implementation.

The adaptation's 17-name strip list adds `requirements_dev.txt` and
`requirements_test.txt`, but removes root-level paths rather than the official
recursive basename walk. Its regex uses the first `(\d+) passed` match in only
the **last command's output**, without the official command-name filter, rather
than summing the official first match per line across pytest commands. Both cap the
fraction at 1 and both trust generated-code-influenced output. These differences
preclude assuming exact protocol equivalence.

**Trust decision:** generated Python can print score-shaped output, influence
pytest hooks/imports, or modify evaluation state in the same execution domain.
No trusted collector resistant to such interference was proved. Native counts
and any future execution output remain **untrusted observations**, with no
certified numerical score or passed verdict until the trusted-collector
requirement and actual-submission binding are demonstrated. A directory-only
split, exit-code check, or JSON/JUnit file in that domain is not sufficient.
Hidden test/procedure content and reference source must never be copied to a
solver workspace; the manifest itself is evaluator metadata, not solver input.

## Images, controls and licensing blockers

Official per-task references are mutable GHCR `<id>:1.0` tags; adaptation
metadata also names `generalreasoning/nl2repobench-<id>:1.0`. Neither pinned
source provides verified content digests. Every manifest digest is `null` and
`verification` is `not_checked`. `prepare_data.py:118–135` invokes
`docker manifest inspect <ghcr-tag>`; this source code is not evidence that a
particular manifest exists now, is pullable, or contains a valid control.

No **known-valid positive control** or **known-valid negative control** is
established. `adaptation/tests.py:105–124` contains an optional, credential-gated
empty-submission assertion `result.reward < 0.1`; it was **not run**, and source
overlay makes its result particularly important to verify. The paper's claimed
reference-suite pass is not a digest-bound control for these image tags. Before
certification require reference-positive, empty/missing-source negative,
deliberately wrong implementation, output-forgery, and isolation/leak controls
on pinned images, with trusted evidence bound to the submitted repository,
specification, procedure and environment.

The adaptation README claims Apache 2.0 but links to official `main/LICENSE`.
**Neither repository's pinned Git tree contains a LICENSE file.** That claim
does not establish a license grant for the official dataset, adaptation code,
per-task reference repositories or image layers. Redistribution authorization
is unresolved, not granted by this audit. Keep acquired assets ignored pending
clarification; do not vendor task text/tests/images based on the README link.

## Acceptance gates still open

- Obtain an authoritative license grant and per-repository/image obligations.
- Resolve and record actual image manifest/content digests and platform.
- Verify clean reference and submission-only evaluation; no inherited source.
- Prevent solver access to hidden procedures, reference source and evaluator
  state with an enforced boundary, not sibling paths.
- Prove a trusted collector against generated-code output/report spoofing.
- Run digest-bound controls and the standalone invocation under explicit live
  opt-in; report operational failures separately from evaluation verdicts.
- Resolve whether future runs target official 104 or a separately pinned and
  explicitly enumerated 103-task subset. Never silently omit unavailable tasks.

Until then this manifest supports **deterministic metadata inspection only**;
it does not certify reproducible native scores or a valid benchmark run.
