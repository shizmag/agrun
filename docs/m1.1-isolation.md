# M1.1 grading isolation boundary

## Trusted callers and API

`Benchmarks::Submission.new(store:)` captures a repository with
`capture(repository:, run_id: "benchmark", step_id: "submission", attempt: 1)`.
The return value is an existing Store repository artifact, not a second artifact
format. `verify(artifact)` looks up the stored ID, checks type/digest/path identity,
checks the tree and asks Store to verify its content. `materialize(artifact,
destination:)` creates a fresh private copy; `verify_snapshot!` checks that copy.
Root symlinks, internal symlinks, special files and hard-linked regular files are
rejected. No submitted manifest or solver-provided destination is accepted.

Trusted adapter code constructs `ContainerGrader::Plan.new(image:, command:
"nl2repo")`. The image must use a complete lowercase SHA256 digest. The only
allowlisted command is `/opt/agru/bin/grade-nl2repo`, which must exist in the
trusted image. There are no arbitrary argv, host mount, environment, privileged,
network or shell options in this API. The adapter, not solver output, selects
the plan. A digest establishes identity, not trust in an image's contents.

`ContainerGrader.new(store:, process_runner: Adapters::ProcessRunner.new).grade(
submission:, plan:, limits:, cancellation: nil)` accepts exactly the resource keys
`cpus`, `memory_bytes`, `pids`, `timeout_seconds`, `tmpfs_bytes`. Values must be
positive finite numbers; byte and PID limits must be integers. Invalid plans or
limits raise `ArgumentError` before subprocess launch. No implicit defaults relax
the resource policy.

## Docker policy

Each call uses a random fresh container name and a private temporary snapshot,
never the mutable Store tree or solver workspace as the container bind source.
The sole bind mount is that internally chosen snapshot at `/submission`, read-only
and private propagation. Docker runs without network, as UID/GID 65534, with a
read-only root filesystem, all capabilities dropped and no-new-privileges.
CPU, memory (including equal memory-swap), PIDs and `/tmp` tmpfs are bounded.
Tmpfs is noexec/nosuid/nodev. There is no Docker socket mount, device grant,
privileged mode or host execution fallback. Image pulling is disabled. Image
entrypoint is explicitly replaced by the allowlisted absolute command. Its sole
argument is the fixed `/submission` path, overriding the image's default CMD.

ProcessRunner executes argv directly and bounds captured stdout/stderr. Timeout
and cancellation terminate the Docker client process group. An unconditional
separate `docker rm --force <name>` follows every attempted run, including daemon
errors, exceptions, cancellation and timeout. Cleanup uses its own ten-second
budget and is not suppressed by cancellation. Cleanup failure is recorded and
makes execution status error. If the daemon cannot remove a container, the
implementation cannot guarantee its removal; the recorded name supports operator
cleanup. Temporary host snapshots are removed on all ordinary return/exception
paths. Host process termination or machine failure can still leave resources.

Source Store evidence and the private snapshot are checked again after execution.
A detected mutation makes execution error, not a valid result. These are integrity
checks, not an OS-level sandbox against a malicious same-user host process.

## Execution evidence is not an authoritative score

The returned hash contains `execution_status`, process status/stdout/stderr,
exit code, duration, truncation indicators, container/image identity, resource
policy and verified submission identity when available. Timeout and cancellation
are distinct. Nonzero exit, truncation, integrity failures and cleanup failures
are errors. There are deliberately no `score` or `verdict` fields.

`result_authority` is always `untrusted`. Even exit zero plus well-formed JSON
such as `{"score":1}` establishes only process completion. Submitted code can
forge stdout or tamper with in-process grading logic. A native adapter may parse
diagnostics, but must not promote this channel into an official score without an
independently validated trusted collector/protocol. The current container runner
does not establish that collector, provision hidden tests, install dependencies,
or certify an official NL2Repo environment. Official readiness remains blocked.

## Validation and limits

Offline recording-runner tests cover argv hardening, fresh names, fixed commands,
no solver mounts, strict resource policies, cleanup on errors/timeouts, forged
JSON, truncation, nonzero exit, filesystem rejection, Store tampering and source/
snapshot mutation. They require no Docker daemon and make no network calls.
Initial Docker validation was blocked by a socket error; the later live synthetic
probe below supersedes that availability observation. Docker's host kernel
isolation is not a stronger VM sandbox;
programs and Ruby adapters remain trusted host code. Arbitrary hostile local
concurrent writers and malicious daemon/image configuration are outside the
guarantees of directory separation and these offline tests.

On Docker Desktop, these flags constrain the container within Docker's Linux VM;
they do not reserve or independently bound the Desktop VM's host CPU, memory,
disk usage or daemon overhead. Effective capacity is also limited by Desktop's
operator-configured VM resource allocation and kernel/cgroup support. This code
does not change those defaults or attest that the daemon enforces every flag.
Daemon-side enforcement must be checked in a real-Docker validation environment
before claiming operational resource isolation. Injected runners are trusted test
seams: the timeout guarantee depends on the production ProcessRunner honoring its
contract, not on preempting arbitrary Ruby implementations of `call`.

### Live synthetic boundary probe — 2026-11-14

At `2026-11-14T16:43:38Z`, Docker Desktop server `29.8.2`, Linux/aarch64,
cgroup v2 became available. Its reported VM allocation was 10 CPUs and
8,319,504,384 bytes RAM. Using only the already-cached image
`alpine@sha256:3f4d6b32e26703c6082839234f43769d5046b3ac7c910033911d1e71d8cd630a`,
the actual `ContainerGrader` returned `execution_status: error`, exit 127, with
`stat /opt/agru/bin/grade-nl2repo: no such file or directory`. This is the expected
environment/setup failure, not a task failure or zero score. Result authority
remained untrusted and score/verdict fields were absent. `docker inspect` before
cleanup confirmed the actual read-only private snapshot mount and resource flags.
Forced cleanup succeeded; exact-name `docker ps -aq` returned no container.

A separate operator-controlled `/bin/sh` diagnostic (not an accepted grading
plan) used the same policy and cached image, without pulls or network. It observed:

- UID/GID 65534, `CapEff: 0000000000000000`, `NoNewPrivs: 1`.
- Root write failed with `Read-only file system`; `/tmp` write succeeded.
- `/tmp` was `rw,nosuid,nodev,noexec,size=1024k`.
- cgroup CPU `100000 100000`, memory `134217728`, swap `0`, PIDs `32`.
- Docker network mode `none`, empty IP/gateway in inspection. Kernel tunnel
  interfaces were listed, so the observation is not described as "only lo".
- A 30-second sleep was terminated at the two-second ProcessRunner deadline
  (measured 2.057 seconds); subsequent forced removal succeeded and exact-name
  listing was empty.

Exact argv, outputs, timing, Docker info and pre-cleanup inspection JSON are local
run state at `.agru/m11-isolation-evidence.json`; its reproducible local probe is
`.agru/m11-isolation-probe.rb`. Neither should be committed. No image was built
or pulled. This is synthetic isolation evidence only: Alpine lacks the trusted
helper, official task assets and validated result collector; no official task or
score was obtained. It does not benchmark resource saturation or prove isolation
against kernel/daemon vulnerabilities.
