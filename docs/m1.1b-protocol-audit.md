## What the pinned implementation actually scores

Primary evidence: official `openhands/post_processor.py:429-482`,
`test_data_service.py:51-57`, `only_test.py:20-37`, and
`openhands/openhands_app.py:263-284` (paths relative to the official cache above).

* Unit: **declared passing test cases per task**, not repository all-or-nothing
  success. The parser sets `total` to the task's `test_case_count.txt` integer.
* For each command whose text contains `pytest`, every output line is searched
  for `(\d+) passed`, `(\d+) failed`, and `(\d+) error`. Matches are added across
  lines and commands, without test identities or deduplication.
* `success_rate = min(passed / total, 1)` when `total > 0`, otherwise zero.
  This is not a dynamically collected-test denominator. The top-level legacy
  `score`/`test_score` fields instead contain the **raw passed count**, not that
  normalized rate. Consumers must identify which field and unit they report.
* Skips, xfails and xpasses have no dedicated accounting. Skips do not subtract
  from the declared denominator; they cannot be treated as passing tests.
* Collection failure, missing pytest, crash and no tests normally yield no
  passing-text matches and hence zero. The parser does not inspect exit codes;
  a preceding or forged pass line can survive an abnormal exit. Post-processing
  `status: success` means its orchestration completed, not that all tests passed.
* A macro mean of per-task rates and pooled passed/declared totals are different
  statistics. Preserve both numerator/denominator and task coverage; never infer
  a benchmark aggregate from legacy raw `score` alone or drop unavailable tasks
  while calling the result the full 104-task benchmark.

| `pytest tests`, fatal-error text, exit 139 | 96 | passed 0, rate 0 |
| `pytest tests`, `no tests ran`, exit 5 | 96 | passed 0, rate 0 |

These demonstrate parser behavior, **not native real-task validation**. Arbitrary
candidate code can print matching text; stdout is not an authenticated result.

Reproduce offline from the existing pinned cache:

```sh
python3 script/m11b_legacy_parser_probe.py
```

An alternative existing cache may be selected with `--cache-root PATH`. The script
checks the complete source SHA256 above before AST extraction; it does not trust
a folder's name as proof of pin identity. It emits JSON containing procedure and
source hashes, extracted-function AST hash, Python version, exact inputs/outputs,
expected results and match flags. Exit 0 means all five diagnostics matched,
1 means a mismatch, and 2 means missing source or failed source validation. Missing
cache is an explicit failure, not a silent skip. It never downloads assets or
imports the upstream module, and includes no redistributed upstream function.

## Overlay, dependencies and contamination

Official `openhands/post_processor.py:187-298,485-545` recursively removes a
fixed list of packaging/configuration files from the submission, deletes exactly
the task-listed test paths, and builds a derived image with
`COPY workspace/ /workspace/` over the original task image. Packaging removal
includes `setup.py`, `pyproject.toml`, `setup.cfg`, requirements variants,
`pytest.ini`, `tox.ini`, locks and manifests. It changes the effective submitted
tree; evidence should retain both original snapshot and transformed-tree digests.

COPY is an **overlay**, not replacement. Unmatched image files remain. The image's
reference implementation, packaging, dependencies and original tests can therefore
affect an empty or incomplete candidate. A positive reference control alone cannot
rule this out: an empty/broken submission and actual import provenance are needed.
No claim that every task leaks reference code is established by static inspection.

Deleting listed test files does not prohibit extra solver tests from being
collected. For `python-pathspec`, the cached metadata lists four individual test
files, but invokes `pytest --continue-on-collection-errors tests`; other generated
test files under `tests/` survive. Root/nested `conftest.py`, import hooks and
candidate runtime behavior are further integrity risks, not fixed by directory
separation or Docker alone.

The official Docker service at `docker_self/docker_service.py:786-788` uses
`shlex.split(command)` followed by direct execution. A shell-based rewrite is a
protocol change, even if it repairs broken setup commands. Dependencies come from
the published image plus declared commands; silently installing pytest, changing
packaging treatment or repairing requirements creates a different environment.

## Licensing and authorization

The adaptation README labels the benchmark Apache 2.0 but links to the official
repository's mutable `main/LICENSE`; that is not a license grant in the audited
official pin. Each original project, image and included dependency can have its
own license. Public visibility, local cache availability and an adaptation's
assertion do not authorize redistribution. Record explicit authorization or
documented applicable grants separately for local solver specification use,
grading-only tests/reference assets, and redistribution. Do not unnecessarily
couple permission to use a private grading cache to permission to redistribute it.

## Feasibility and limits

Existing authorized assets can support **limited controlled local validation**:
grading-only reference overlay, empty/broken negative control, pinned native
commands, raw logs/exits and actual environment identity. Reference material must
never enter the solver workspace. This audit does not block those harmless,
explicitly opted-in controls merely because strong adversarial isolation is not
yet proved. They must be labeled trusted controls, not strong official scores.

Strong adversarial score authority additionally needs a collector/result channel
that candidate code cannot write or impersonate, hidden-source confidentiality,
submission snapshot integrity, provenance of imported code, and demonstrated
resistance to forged output/process interference. Under
`docs/m1.1-contracts.md:73-95`, those unresolved gates mean blocked/untrusted with
no authoritative score. Neither a successful native reference run nor Docker
alone discharges them. No real-task/native readiness claim is made by this audit.
